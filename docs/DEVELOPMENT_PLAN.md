# 祁智运总体设计与开发文档

## 1. 项目定位

平台服务祁东县黄花菜采收、加工与城乡配送场景。它不是通用 ERP，而是以算法决策为核心的县域物流调度工作台，突出第二赛道要求的 AI 智能调度、路径规划、动态响应和效果评估。

主要用户包括县域共配中心调度员、乡镇/村级网点、承运企业、加工企业和管理部门。

## 2. 业务闭环

```text
订单与车辆数据
  → 构造容量、时间窗、冷链兼容约束
  → OR-Tools 生成车辆路径
  → 地图展示线路、停靠顺序与指标
  → 车辆故障/紧急订单事件
  → 移除故障运力并重建剩余任务
  → 新方案下发与优化效果对比
```
0
MVP 使用 12 个村级订单、5 台车辆和祁东县共配中心进行演示，其中 4 个订单要求冷链运输。

## 3. 功能设计

### 3.1 智能调度

- 展示订单量、货量、冷链订单与准时率。
- 计算 CVRPTW：带容量和时间窗的车辆路径问题。
- 将“冷链订单只能由冷链车辆承运”建模为硬约束。
- 输出车辆、里程、装载率、停靠顺序和预计到达时间。
- 对比优化前后的总里程、空驶率、成本和车辆数。

### 3.2 动态事件

- 模拟冷链车 `湘D·A1234` 故障。
- 从可用运力集合移除故障车辆。
- 加入紧急冷链订单并重新求解。
- 展示事件识别、约束重建、增量求解、方案下发四步链路。
- 给出受影响订单、延误、冷链约束满足率和 AI 解释。

### 3.3 可视化

- 使用祁东县离线 GeoJSON，保证答辩现场断网可运行。
- ECharts 绘制县域边界、节点、车辆路线和动态流向。
- 桌面端按 1440×900 竞赛演示屏设计。

### 3.4 AI 解释服务

- 系统设置提供管理员登录、服务商地址、模型 ID、温度和启停配置。
- 支持实现 `/chat/completions` 的 OpenAI 兼容服务，不在代码中绑定具体模型。
- API Key 使用独立 Fernet 密钥加密后写入 PostgreSQL，读取接口只返回掩码。
- 大模型用于调度结果解释和辅助建议；OR-Tools 仍负责可验证的容量、时间窗、冷链和路径约束。
- 对外只发送聚合指标与脱敏线路摘要，不发送账号密码、数据库连接或 API Key。

## 4. 技术选型

| 层级 | 选型 | 理由 |
|---|---|---|
| 前端 | Vue 3、TypeScript、Vite | 开发快、类型明确、组件化适合大屏 |
| 可视化 | Apache ECharts | GeoJSON、线路和动态散点能力完整 |
| 图标 | `@lucide/vue` | 统一线性图标，避免手绘 SVG |
| 后端 | FastAPI、Pydantic | 接口契约清晰，自动生成 OpenAPI |
| MVP 求解 | Google OR-Tools | 成熟支持容量、时间窗和车辆兼容约束 |
| 进阶求解 | PyVRP | 可用于更大规模、多仓、多车型与算法对比 |
| 道路矩阵 | MVP 为 Haversine×乡村绕行系数 | 离线稳定、便于演示 |
| 生产道路矩阵 | OSRM 或高德/百度接口 | 获取真实路网距离和行驶时间 |
| 数据库 | PostgreSQL + PostGIS | 支持方案、事件、模型配置和空间查询 |
| 缓存与任务 | Redis + Celery | 异步求解与任务状态 |
| AI 接口 | OpenAI-compatible HTTP API | 可替换服务商，避免平台锁定 |

## 5. 求解模型

目标函数以最小化总行驶距离为主，并通过车辆固定成本减少车辆启用数量。约束包括：

- 每个订单只访问一次；
- 车辆累计载重不超过容量；
- 到达时间处于订单时间窗；
- 车辆工作时段有效；
- 冷链订单禁止分配给常温车辆；
- 故障车辆不得进入重调度方案。

当前道路距离按两点球面距离乘 `1.28` 的县乡道路绕行系数估算，平均速度按 `42 km/h` 估算。正式比赛数据接入真实路网矩阵后无需修改求解接口。

## 6. 系统架构

```text
Vue 3 SPA
  ├─ 调度中心
  ├─ 事件中心
  ├─ 数据中心
  ├─ 算法对照实验室
  ├─ AI 系统设置
  └─ ECharts 县域地图
          │ REST/JSON
FastAPI
  ├─ 场景与指标接口
  ├─ OR-Tools 求解服务
  ├─ 动态重调度服务
  └─ AI 配置与解释服务
          │
PostgreSQL/PostGIS + Redis/Celery
```

## 7. 数据实体

- 节点：名称、经纬度、类型（中心/乡镇/加工点/村）。
- 订单：服务节点、重量、时间窗、服务时长、冷链、优先级。
- 车辆：车牌、容量、单位里程成本、冷链能力、班次。
- 路线：车辆、停靠点、到达时间、累计载重、里程和耗时。
- 事件：类型、影响车辆、发生时间和紧急订单。
- AI 服务配置：服务商、接口地址、模型、加密密钥、启停状态和连接测试结果。
- 算法实验：场景版本、SHA-256 指纹、压力规则、求解时限、逐案例指标和实验摘要。

## 8. 开发阶段

1. MVP：离线场景、约束求解、地图路线、故障重调度（已完成）。
2. 部署基础：PostgreSQL/PostGIS、Alembic、Redis/Celery、JWT 与 Docker Compose（已完成）。
3. 数据增强：Excel 导入、真实道路矩阵、历史订单需求预测。
4. 业务增强：完整角色权限、司机确认、方案审批和报表导出。
5. 竞赛完善：真实企业数据校准、算法对照实验、答辩演示脚本。

当前第三阶段已完成第一批数据增强：标准 Excel 模板、场景整批校验、不可变版本快照、单一激活版本和历史方案 AI 解读。真实路网矩阵与需求预测进入下一批任务。

当前第四阶段已完成路网与预测增强：OSRM Table 距离/时间矩阵、异常回退、矩阵缓存、七日需求预测、乡镇需求排行、建议运力和竞赛决策驾驶舱。司机导航级道路几何、连续真实订单训练和实时拥堵权重仍属于后续校准任务。

当前第五阶段已完成业务执行闭环：方案提交审批、管理员审核、车辆任务下发、驾驶员接单/发车/完成、状态汇总、审计日志和执行报告。真实司机移动端、GPS 轨迹和电子签收图片仍属于后续企业数据接入范围。

当前第六阶段已完成竞赛证据闭环：约束校验业务基线、标准/旺季/冷链三压力案例、OR-Tools 同口径对照、场景 SHA-256 指纹、实验留痕、结果可视化与自包含实验报告。真实企业历史样本的参数校准和多求解器横向基准仍属于下一阶段。

## 9. 已知边界

- 当前为单仓取送演示，没有接入真实 GPS、WMS 或支付系统。
- 距离为估算值，不能用于真实司机导航。
- PyVRP 已作为进阶依赖和技能准备，MVP 实际求解器为 OR-Tools。
- 前端主要面向桌面调度屏，移动端仅作为后续司机端方向。
