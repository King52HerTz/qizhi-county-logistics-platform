# 第十六阶段开发文档：空间坐标快照与调度链路一致性

## 1. 阶段目标

第十五阶段完成了网点真实位置校准。本阶段将核验坐标贯通到场景发布、OR-Tools 求解、路线结果、动态事件和地图展示，同时保持业务场景版本不可被静默修改。

核心原则：

- 网点校准属于主数据修改。
- 调度求解只读取已发布场景内的不可变坐标快照。
- 主数据坐标发生变化后，系统明确提示“待重新发布”，不会暗中改写历史场景。
- 每次动态事件必须携带或解析出真实位置，并随调度运行结果永久保存。

## 2. 坐标数据链路

```text
空间校准（GCJ-02）
        ↓
基础数据主表 + WGS-84 标准坐标
        ↓
基础数据发布
        ↓
不可变空间坐标快照
        ↓
OR-Tools 距离矩阵与约束求解
        ↓
路线停靠点 / 动态事件 / 运行历史
```

## 3. 场景空间快照

场景新增以下元数据：

- `spatial_snapshot_id`：基于节点编号、坐标、核验状态和核验时间生成的内容指纹。
- `spatial_snapshot_at`：快照生成时间。
- `spatial_verified_nodes`：快照内已核验网点数。

场景节点同时保存：

- GCJ-02 展示和求解坐标。
- WGS-84 标准交换坐标。
- 坐标来源、核验状态、精度和核验时间。

旧场景保持兼容，缺少快照字段时按“历史场景坐标”处理。

## 4. 发布约束

基础数据发布时执行：

- 必须且只能存在一个启用的配送中心。
- 订单引用的网点必须存在并启用。
- 所有网点必须位于祁东县业务范围。
- 配送中心固定为求解器的起终点，不再依赖数组第一项。
- 未核验网点进入发布警告，提示完成核验后重新发布。

本阶段不自动覆盖当前激活场景，避免破坏版本审计和历史方案可复现性。

## 5. 空间同步状态

新增接口：

`GET /api/v1/scenario/spatial-status`

返回：

- 当前场景快照编号与时间。
- 场景节点数和已核验数。
- 主数据中已核验节点数。
- 坐标已变化、节点缺失和未核验的网点编号。
- 是否与当前主数据完全同步。

调度地图显示：

- “坐标快照已同步”。
- “N 个坐标待发布”。
- “N 个坐标待核验”。

## 6. OR-Tools 求解输入

求解器在构建距离矩阵前检查：

- 场景必须且只能有一个配送中心。
- 每个订单引用的网点必须存在。
- 配送中心按 `kind=depot` 显式查找。
- 求解说明记录本次使用的空间快照编号。

路线结果中的每个停靠点继续携带经纬度，前端地图直接使用结果坐标，不再对已发布场景做浏览器临时地理编码覆盖。

## 7. 动态事件位置

事件请求支持：

- `node_id`
- `longitude`、`latitude`
- `location_name`

解析优先级：

1. 请求明确提交的 GCJ-02 坐标。
2. 请求提交的场景网点。
3. 当前冷链订单所在网点。

事件结果新增 `event_location`，包含位置名称、经纬度、坐标系和来源。该位置同时写入：

- 调度响应。
- 优化运行输出。
- 动态事件详情 JSON。
- 在线和离线事件地图故障标记。

## 8. 前端调整

- 调度地图显示空间快照同步状态。
- 节点详情显示“已核验快照、待复核快照、未核验快照”。
- 模拟车辆故障时，从实际冷链路线选择车辆和停靠点。
- 事件页显示真实车辆、真实位置和真实故障标记。
- 移除对场景坐标的浏览器临时覆盖，保证地图与求解输入一致。

## 9. 测试范围

- 配送中心不是数组第一项时仍能正确求解。
- 多配送中心或订单引用缺失网点时返回不可行结果。
- 空间快照指纹稳定生成并随场景发布保存。
- 校准坐标变化后同步状态返回“待发布”。
- 动态事件坐标进入响应、运行历史和事件记录。
- 高德在线地图和离线地图均使用同一事件坐标。
- 桌面端、移动端、控制台和交互回归测试。

## 10. 完成标准

- 调度求解、路线展示和事件标记使用完全相同的场景坐标。
- 校准主数据不会静默改变历史方案。
- 坐标变化可以被运营人员明确发现并通过发布流程生效。
- 故障标记不再依赖前端固定坐标。
- 所有新接口和界面通过自动化测试与 Docker 环境验收。
